# 스토어 발송 상태·반응성 점검

2026-10-22. 사용자 승인에 따라 무비스·업체 검색 변경과 함께 배포한다. 완료 버전은 [배포 기록](DEPLOYMENT-2026-10-22.md)에 기록한다.

## 확인된 원인과 수정

- 발송 큐 저장, 네이버 API 성공, 배송중 동기화는 서로 다른 시점이다. 기존 UI는 실시간 이벤트 때 전체 주문/상품 조회가 끝날 때까지 기다렸고, 이벤트 누락 시 45초 폴링에 의존했다.
- 주 상태 배지는 `order_status`를 사용하지만 단계 위젯은 `naver_dispatch_succeeded_at`도 사용하여, 성공 직후 발주확인 배지와 발송 위젯이 잠시 달라질 수 있었다. 성공 기록을 공통 상태 판정에 반영했다. 상품별 배송중·배송완료 및 취소 상태를 우선하며 송장번호 입력만으로 성공을 추정하지 않는다.
- 실시간 이벤트에 변경 행을 전달해 배지를 먼저 갱신한다. 후속 전체 조회는 300ms 묶음 처리하고, 이전 조회가 새 상태를 덮지 않도록 요청 순서를 확인한다.
- 큐 처리 중 5초 간격으로 대상 주문 ID의 상태 컬럼만 조회한다. raw_payload, 상품, 이미지 재조회는 하지 않는다. 전체 목록의 45초 안전망과 포커스 복귀 갱신은 유지한다. 숨은 탭은 주기 조회를 건너뛰고, 요청이 진행 중이면 중복 폴링하지 않는다.
- 처리 중/확인 필요 표시를 추가하고, 성공 후 오래된 발주확인 보조 배지를 숨긴다. 재시도 등록 시 이전 발송 오류를 비운다. 내부 주문 ID 목록이 바뀌지 않으면 포장 상태를 다시 요청하지 않는다.
- 고정된 ‘60초 안에 처리’ 안내를 실제 성공 응답 후 자동 갱신 안내로 바꿨다.

## 검증

- 전체 자동 테스트: 172 통과 / 0 실패 / 1 건너뜀 (`MOVIS_TEST_URL` 미지정).
- 단위 시나리오: 대기·실패·송장 입력만 있는 상태, 성공 기록 선행, 배송중·배송완료, 취소, 위젯 숫자, 대상 ID 조회/중복 제거/API 실패.
- 로컬 `?dispatchCheck=1`: 실제 저장·외부 발송 없이 대기→성공→배송중 및 실패 전환, 컴팩트/카드, 실시간 알림 없는 폴링 갱신 확인. 브라우저 오류 로그 없음.
- 390×844: 수평 넘침 없음, 송장 버튼 높이 44px. 기존 무비스 1280/390/360px 모션 검증은 [별도 기록](CUSTOMER-SEARCH-MOTION-2026-10-22.md) 참조.
- 운영 읽기 전용 확인: 최근 발송 2건은 발송 성공 시각 존재, 큐 해제, 대표 상태 shipped, 상품별 상태를 반영한 표시는 모두 DELIVERING. 사용자가 본 배송중 전환과 일치했다.
- 새 대상 상태 조회 API HTTP 200. 2건 응답은 두 번의 관측에서 81ms / 391ms. 성능 보장 수치가 아닌 이 환경의 측정값이다.

## 범위·한계

- 매장 PC `.env`의 동기화 설정은 30초. 실제 실행 프로세스의 설정 재적용 여부까지 확인한 것은 아니다. 이 작업은 웹의 표시 지연과 조회 부하를 개선하며, 매장 브리지/네이버의 처리 속도·재시도 주기는 변경하지 않는다.
- 5초는 보조 조회 간격이며 네트워크·서버 응답 지연을 포함한 완료 시간 보장이 아니다. 실물 iOS/Android와 실제 발송 쓰기는 테스트하지 않았다.
- 상품별 원본 상태가 존재하는 발송 상세는 마지막 동기화 자료를 유지한다. 원본 상태가 없는 경우에만 주문의 확인된 성공 상태를 보조 값으로 사용한다.
