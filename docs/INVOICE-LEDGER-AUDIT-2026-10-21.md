## 결론과 적용 범위

입출금 이력에서 저장 잔액을 계산하는 현재 DB 함수는 검증한 사례에서 정상이다. 그러나 명세서 표시 계산에는 선입금 이월 누락과 수기 명세서 금액 누락이 있었고, 운영 주문과 입금 원장의 금액이 다른 3건도 확인했다. 따라서 시스템 전체를 정상으로 판정하지 않는다.

아래 기록은 배포 전 점검 결과다. 검증된 프런트엔드 수정의 배포 결과는 [2026-10-21 배포 기록](DEPLOYMENT-2026-10-21.md)을 참고한다. 운영 주문·입출금·원장 금액과 SQL은 변경하지 않았으며 기존 3건을 자동 보정하지 않았다.

## 확인 방법

- 코드: 명세서 페이지, 입출금/일괄 입금 모달, 업체 상세, 대시보드, API 조회, Excel 집계, SQL 재계산 함수.

### [P1] 주문 수정·반품 후 원장 금액 불일치 — 자료 정정 필요

주문 순금액과 원장 총액이 아래처럼 다르다. 주문 금액 변경에 맞춰 기존 원장을 재계산하는 DB 트리거가 확인되지 않았고, 현재 입출금 트리거는 순입금만 갱신한다. 따라서 반품·금액 수정 후 원장 금액이 남아 미수가 과대/과소 표시될 수 있다. 개별 변경의 과거 실행 경로까지 확정한 것은 아니다.

| 구분 | 확인 사항 |
|---|---|
| 불일치 A·B | 전액 반품 주문과 기존 원장 총액이 다름 |
| 불일치 C | 주문 순금액과 저장 원장 총액이 다름 |

공개 문서에는 주문번호·원장 ID·개별 거래 금액을 수록하지 않는다. 세부 대조 결과는 매장 PC 로컬 감사 기록에 보관한다.

원장 정정은 실제 청구·반품·환불 내역을 확인한 뒤 해야 한다. 이번 코드는 해당 불일치 자료가 선택 명세서의 당기/이월 범위에 포함되면 경고하고 앱의 PNG·인쇄·카톡 출력 버튼을 차단한다. 이는 원장 정정이나 DB 동기화 구현을 대신하지 않는다. 잔액 0인 과거 건이 이월 범위에서 제외되면 해당 화면 경고에도 나타나지 않으므로 위 감사 목록을 별도로 확인해야 한다.

## DB 함수 검증

현재 `recalc_payment_record`는 이전/새 원장 ID를 정렬해 `FOR NO KEY UPDATE`로 잠근 뒤 입금−출금을 다시 합산한다. `balance`는 `total_amount - paid_amount` 생성 열이다. 2026-10-15 마이그레이션과 현재 조회 함수의 해당 로직이 일치했다.

`tests/payment-db-concurrency.mjs` 결과:

- 입금·출금·출금액 수정·이력 삭제 후 재계산 통과.
- 이력을 다른 원장으로 옮기면 이전 원장 순입금도 0으로 복구.
- 두 연결에서 100원과 200원을 동시에 등록하면 현재 함수는 300원. 수정 전 함수는 200원으로 누락되는 비교 사례 재현.
- 같은 요청 안의 일괄 INSERT 중 FK 실패가 발생하면 전체 롤백.

로컬 PostgreSQL 버전은 17.10이다. 운영 환경에서 테스트 입금/삭제를 실행한 것은 아니며, 운영 실제 34개 이력 대조와 함수 정의 확인을 함께 근거로 사용했다.

### 남은 서버 수준 보완

- **[P1] 요청 중복 방지 부재:** 같은 업무 요청을 다른 ID로 두 번 보내면 둘 다 저장된다. UI의 중복 클릭 방지/실패 후 재시도 잠금은 있으나 새 창·다른 기기·전송 재실행까지 보장하지 않는다. 서버의 요청 키와 유일 제약이 필요하다.
- **[P2] 신규 원장+첫 입금이 별도 요청:** 원장 생성 후 입금 저장이 실패하면 입금 없는 원장이 남을 수 있다. 격리 DB에서 재현했다. 하나의 서버 트랜잭션으로 묶는 작업이 필요하다.
- **[P2] 일괄 배분의 조건부 저장:** 저장 직전 최신 잔액을 다시 읽지만 조회와 INSERT 사이의 다른 PC 입금까지 잠그지는 못한다. 서버에서 잠금·잔액 검증·입력 저장을 함께 처리해야 한다.
- **[P2] 서버 금액/종류 제약:** 조회한 관련 테이블 제약은 PK/FK 중심으로, 금액/종류 CHECK가 확인되지 않았다. UI 검증 우회까지 막는 DB 제약이 필요하다.
- 선입금은 업체 합계에서 차감한다. 선입금 원장과 개별 미수 원장을 대체전표로 상계해 각 건을 완납으로 만드는 기능은 이번에 추가하지 않았다. 업체 순잔액 0이어도 개별 양수/음수 원장이 남을 수 있다.
- 과거 UTC 기반으로 저장된 거래일은 일괄 변경하지 않았다. 새 생성/표시 계산에 KST를 적용했다.

### 실제 로컬 화면에서 확인한 시나리오

샘플 구성: 이전 미수 70,000원, 이전 선입금 −20,000원, 당기 상품 55,000원 중 순입금 5,000원(입금 7,000−출금 2,000), 수기 명세서 33,000원.

1. 합계 `50,000 + 88,000 - 5,000 = 133,000원` 표시.
2. 이전 상세를 포함해도 `228,000 - 95,000 = 133,000원` 유지.
3. 당기 단가를 인쇄용으로 5,000원 올리면 인쇄 잔액 138,000원, 실제 원장 잔액 133,000원 안내. 원본 복원 후 133,000원 복귀.
4. 일괄 입금 전액 버튼 133,000원. 오래된 순 70,000 / 50,000 / 13,000 배분.
5. 샘플 저장 403 실패 시 성공 처리하지 않고 재저장 버튼 잠금.
6. 업체 상세 미수 133,000원, 이력 4건 확인. 입금 등록으로 이동하면 해당 업체 ID 1 자동 선택.
7. `invoiceCheck=mismatch`: 차액 경고 표시, 출력 버튼 비활성화 확인.
8. `invoiceCheck=failure`: 조회 실패 안내, 출력 버튼 비활성화 확인.

샘플 화면 검증 중 브라우저 경고창 제어가 멈춘 1회가 있어 새 테스트 탭에서 후속 확인을 진행했다. 실제 프린터 출력, 카톡 전송, 운영 입금 등록은 실행하지 않았다. 1차 Excel 검증은 코드 검토/빌드 범위였다. 아래 2차 검토에서 실제 생성 xlsx를 다시 읽는 자동 검증을 추가했다. Excel 앱에서의 수동 시각 검수는 하지 않았다.

### 여전히 필요한 서버/장부 보완

- 운영 완불 표시 4건은 실제 입금 확인 후 원장과 연결해야 한다. 표시만 믿고 자동 입금하거나 과거 입금일을 오늘로 바꾸지 않았다.
- 기존 주문·원장 차액 3건의 실물 자료 정정과 주문 수정/반품의 원장 자동 동기화는 이전 절차대로 필요하다.
- 완불 처리/취소는 여전히 여러 HTTP 요청이다. 중간 실패 시 이미 반영된 입금/취소가 일부 남을 수 있으며 알림과 재조회로 드러낸다. 전부 롤백되는 서버 트랜잭션이라고 보장하지 않는다.
- 같은 브라우저 중복 클릭 차단은 다른 탭·PC·직접 API 재전송까지 해결하지 않는다. 서버 요청 키·유일 제약·잠금·조건부 저장은 별도 적용이 필요하다.
- 현재 원장 값이 잘못된 상태에서 자동으로 덮어쓰기보다 확인을 요구하도록 했다. 일부 완불/동기화 동작이 기존보다 보수적으로 중단되는 것은 의도된 변경이다.
