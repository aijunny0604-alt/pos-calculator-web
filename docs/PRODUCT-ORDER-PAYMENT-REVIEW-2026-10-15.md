## 제품 주문 개선

- 상품명·규격, 재고, 단가, 수량을 비교하는 목록형 기본. 기존 이미지 카드 보기로 전환 가능.
- 즐겨찾기는 이 브라우저에 저장. 상품 보기 방식도 유지.
- 거래처를 주문 전에 선택하고, 주문 확인에 이름·연락처·주소를 전달.
- PC 고정 주문 목록에 거래처와 도매/소매 기준 표시. 모바일 하단 주문 확인 유지.
- 최근 5개 주문 다시 담기는 현재 상품 정보/단가를 사용하며 기존 장바구니에 추가. 삭제된 상품이나 잘못된 수량이 있으면 전체 추가를 중단한다. 과거 할인/특가는 복사하지 않는다.
- 카테고리 안쪽 중첩 스크롤 제거.
- 실제 상품이 없을 때 오래된 하드코딩 가격표를 대신 판매 목록에 표시하던 동작 제거.

## 검색

순서가 바뀐 단어, 붙여 쓴 역순 단어, 초성, 전각 숫자, 동의어를 처리한다. 정확한 토큰과 숫자 규격 일치를 우선하고, 소수점 규격을 구별한다. 카테고리 필터를 검색 전에 적용하고 18개 제한으로 뒤의 정상 결과가 누락되는 문제를 없앴다. 결과를 최소 6개까지 채우던 강제 후보 삽입도 제거했다. 자동 쓰기 도구의 단건 상품 선택 로직은 변경하지 않았다.

검증 예: `밴딩 스텐 30 54`, `54/30 스텐 밴딩`, `밴딩스텐 54-30`, `ㅅㅌ ㅂㄷ 54 30`, `밴드 STS ５４ ３０`. 60.5와 65, 5와 65를 별도 규격으로 취급한다.

## 운영 DB 읽기 전용 검증

Supabase 관리자 화면에서 정의 및 집계 SELECT만 실행했다. 운영 PostgreSQL 버전은 17.6이다.

- `trg_recalc_payment`: payment_history의 INSERT/UPDATE/DELETE 후 실행.
- 실제 함수는 income을 더하고 expense를 뺀다.
- balance는 total_amount-paid_amount 생성 열이다.
- 현재 이력 합계와 paid_amount 불일치 0건, balance 산식 불일치 0건.
- 유효하지 않은 금액/입출금 구분 0건, 주문별 중복 payment_records 0건.
- payment_history의 요청 식별/멱등 키 컬럼은 없다. 금액/구분 CHECK도 현재 제약 목록에 없다.

## 격리 PostgreSQL 재현

npm `embedded-postgres@17.10.0-beta.17`의 PostgreSQL 17.10을 별도 작업 폴더에 설치했다. 서비스 등록 없이 127.0.0.1:55437로만 실행하고 테스트 후 종료했다. 운영 접속 정보나 운영 데이터를 복제하지 않았다. 운영에서 확인한 트리거 본문과 필요한 최소 테이블 구조, 가상 금액만 복제했다.

| 시나리오 | 현재 함수 복제본 | 수정안 |
|---|---|---|
| 입금 400 - 출금 50 | 350 통과 | 350 통과 |
| 출금액 100으로 수정 | 300 통과 | 300 통과 |
| 출금 삭제 | 400 통과 | 400 통과 |
| 이력을 다른 명세서로 이동 | 원래 명세서 400이 남음 | 원래 명세서 0으로 재계산 |
| 일괄 요청 중 잘못된 FK | 전체 롤백 통과 | 전체 롤백 통과 |
| 서로 다른 세션에서 100+200 동시 입금 | **200으로 누락 재현** | **300 통과** |

수정안: `supabase/migrations/20261015_payment_recalc_lock.sql`. 부모 명세서를 정렬된 순서로 `FOR NO KEY UPDATE` 잠근 다음 별도 SQL로 집계하고, 내역 이동 시 이전/새 명세서를 모두 재계산한다. 2026-10-15 운영에 적용하고 함수 정의와 합계 일치를 재확인했다.

웹 코드에서도 자동 완불 처리 후 오래된 paid_amount를 다시 덮어쓰지 않고 DB 결과를 재조회한다. 자동 입금 취소 후 부모 명세서를 삭제하던 동작도 제거해 동시 입금 이력이 CASCADE 삭제되는 경로를 없앴다.

## 추가로 확인된 구조적 한계

- 동일 요청을 새 이력 ID로 다시 전송하면 서버는 별도 입금 두 건으로 저장한다. UI 중복 클릭 잠금/실패 후 재확인은 적용했지만, 재시작·다중 PC를 포함한 서버 멱등성은 보장하지 않는다. 요청 UUID와 유일 제약을 사용하는 서버 저장 함수가 후속 개선 대상이다.
- 새 명세서 생성과 입금 저장은 두 요청이다. 두 번째 실패 시 첫 명세서가 남는 것을 로컬에서 확인했다. 화면은 재확인을 안내하지만 두 요청 전체의 원자성은 보장하지 않는다. 서버 단일 트랜잭션 저장 함수가 후속 개선 대상이다.
- 위 두 한계는 테스트를 생략한 것이 아니라 현재 동작을 재현한 결과다. 운영에는 거래가 없는 테스트 행도 추가하지 않았다.
