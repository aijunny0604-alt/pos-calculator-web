### 배포 후 MOVIS 실사용 점검 (21:44~21:48 KST)

매장 PC의 로컬 브리지가 실행되지 않아 시작한 뒤, 최신 빌드의 localhost 화면에서 GPT 연결과 단순 계산 응답을 확인했다. 상품 수의 실제 조회는 한 번 연결 오류가 발생한 후 읽기 전용 재시도에서 DB 직접 조회와 같은 결과를 반환했다. 업무 자료는 변경하지 않았다. 별도 Node 실행에서 동일 loader의 22개 테이블 모두 complete로 조회되었으나 브라우저에서는 일부 자료 연결 실패도 관찰했다.

공용 GitHub Pages 화면에서는 이 점검 브라우저의 localhost 연결이 계속 실패하여 웹 경로까지 정상이라고 판정하지 않았다. 로컬 네트워크 접근 허용/브라우저 연결 환경 확인이 남아 있다. 단순 응답 성공을 전체 보관함·변경 업무 검증 완료로 해석하지 않는다.

서버는 Healthy였고 핵심 5개 REST 읽기가 모두 HTTP 200(약 89~198ms)으로 응답했다. 조직 사용량 화면은 현재 결제 주기의 Free 한도 미초과를 표시했다. 조회한 최근 DB/API 오류는 복구 전후에 집중되어 있었다. Disk IO 요약 경고와 제공사의 Realtime 장애 모니터링 공지는 남아 있으므로 지속적인 무장애를 보장하지 않는다. 상세 운영 수치와 화면은 로컬 점검 자료에만 보존한다.

후속 운영 배포 검증: Pages `built`, 운영 index/참조 자산 8개와 로컬 빌드 해시 일치, 실제 브라우저의 새 번들 로딩 및 대시보드 ONLINE을 확인했다. [배포 기록](DEPLOYMENT-2026-10-13.md).

`node --test tests/*.test.mjs`: 격리된 로컬 브리지에 `MOVIS_TEST_URL`을 지정하면 83개 통과, 실패/건너뜀 0개. 변수가 없으면 HTTP 접근 제어 검사 1개를 건너뛴다. `npm run build` 성공, 큰 청크/import 혼용 경고는 남는다. 브리지 검사는 GPT 대화나 운영 DB 쓰기를 수행하지 않는다.

추가 검사: 핵심 목록의 null 실패 처리, GET 제한 신호와 쓰기 재시도 금지, MOVIS 동시 조회/취소/전체 제한, 실시간 이벤트 중복 방지 및 구독 해제, 출력 HTML 이스케이프.

로컬 브라우저 fixture에서 OFFLINE → 모의 서버 복구 → 새로고침 없이 ONLINE 전환을 확인했다. 정상 재설치(`npm ci --ignore-scripts`)도 peer dependency 우회 옵션 없이 통과했다. Windows에서 실행 중인 Vite가 esbuild 파일을 잠글 수 있으므로 재설치 전 개발 서버를 종료한다.

장애 복구 UI 재현: `npm run dev -- --host 127.0.0.1 --port 5175 --strictPort` 후 `/pos-calculator-web/tests/pos-recovery.html`을 연다. 이 fixture는 외부 fetch를 모의 응답으로 대체하고 WebSocket을 차단한다. 처음 OFFLINE을 확인한 뒤 '모의 서버 복구'를 누르면 재시도 주기에 ONLINE으로 바뀌어야 한다. 운영 고객 자료를 넣지 않는다.

이번 운영 확인은 읽기 전용이다. 주문·상품·거래처·장바구니·결제 제한 조회의 HTTP 200, POS ONLINE 및 주요 화면 로딩을 확인했다. 실제 주문 생성·삭제, 결제 수정, 두 PC 동시 재고 변경, 운영 realtime 쓰기 전파, 구형 실물 모바일은 검증하지 않았다. 아래 과거 체크 항목은 이번에 재실행한 결과가 아니다.

잔여 위험은 [최신 점검 보고서](AUDIT-2026-10-13.md) 참조. 의존성 검사: production moderate 2개/high 0개, 전체 moderate 4개/high 5개. 강제 메이저 업데이트를 하지 않았다.
